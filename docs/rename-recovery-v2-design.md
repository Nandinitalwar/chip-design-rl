# Rename recovery v2 — starter design and difficulty rationale

Status: draft 2, final root-authorized move-alias-only strengthening; awaiting contract closure before implementation.

## Evidence motivating this change

`docs/blind-attempt.md` reports one fresh Astra/high success in 288.415 seconds. `docs/blind-attempt.patch` changes only three local conditions: retain incomplete ownership, always apply lane-0 map update, and match completion identity. This is qualitative evidence that v1's starter already supplied almost all of the solution algorithm; it is not a measured pass-rate estimate. Preserve that trial and all earlier task evidence unchanged.

## Proposed original starter

Build a small, working **legacy one-inflight, non-speculative** implementation behind the same public top-level interface. It provides practical integration scaffolding and a functioning ordinary-instruction path without providing a nearly complete two-wide recovery algorithm.

- `design.sv`: one pending instruction record, a committed architectural map, and completion/retirement control. Accept only lane 0, only when idle and the proposed instruction is neither a branch nor a move. Both completion ports work independently and match identity plus destination. Expose one completed retirement record; retain it under backpressure; commit its effective destination mapping. Reset clears the pending record and initializes the map. Completion does not bypass into retirement. It does not contain alias ownership/provenance machinery, a ROB array, a multi-record next-state transition engine, checkpoint masks, branch-resolution machinery or rollback reconstruction.
- `map_bypass.sv`: legacy committed-map lookup for one lane's two sources and stale destination. Sources are ready because every accepted instruction starts with no prior live instruction. No speculative-map replay or same-bundle bypass algorithm is supplied.
- `ownership.sv`: choose one tag outside the committed map and pending destination, with a straightforward legal priority. No multi-destination reservation, speculative ownership/recovery state, or dual allocation is supplied.
- Public `smoke.sv`: reset, accept one ordinary writer, complete it on port 1, hold/retire it, and accept a later dependent instruction. It demonstrates the existing wiring and legal handshake without providing a private scoreboard or the missing algorithm.
- Public README: state exactly what the legacy controller supports and what the upgrade requires. The starter's conservative stalls/branch refusal are explicitly incomplete for the requested product. Do not imply that the full contract can be restored by correcting a few suspicious predicates.

All implementation RTL is original. The new source will not be generated by mutating the full oracle. The top-level interface remains exactly the reviewed interface, but internal helper interfaces can match the smaller legacy design and can be changed freely by the candidate.

## Adversarial easiest plausible solution

The easiest legitimate design remains compact reconstruction: maintain the committed map and live instruction history, derive ownership as a set of all still-referenced tags, and derive readiness from allocating producers rather than move records. This algorithm is allowed and may remain easy for Astra; no unsupported numerical difficulty claim is made. This is allowed. The legacy starter supplies none of the multi-record reconstruction, alias provenance, dual admission, or recovery transition engine. Only the single-instruction wiring and ordinary life cycle work.

The first unchanged-contract plan made that reconstruction too close to direct v1 transcription. The authorized strengthening adds shared-tag move elimination. The candidate must now distinguish mapping updates from physical allocation, preserve ready values across incomplete aliases, prevent completed aliases from waking pending producers, avoid freeing stale tags still owned elsewhere, and admit aliases without free physical capacity. These interact with lane order, zero/self moves, source overwrite, multiple committed aliases, late killed completions and same-edge retirement/recovery.

The proposed ownership set equation is intentionally public: withholding the invariant would be a hidden rule, not productive difficulty. Its implementation must be integrated with readiness provenance and event state, which are not supplied by the starter. A solver who writes a correct small implementation should pass. No honest review can promise this will yield only one success in five; the bounded batch will test that hypothesis.

## Work the candidate must supply

The one pending record cannot represent two accepted instructions, much less a bounded retirement queue. To satisfy the public throughput and recovery contract, the candidate must create a multi-record state representation and connect several decisions: maximal-prefix admission against three resource limits; speculative and intra-bundle mappings; separate live destination ownership from committed ownership; two-wide retirement and stale reclamation; checkpoint lifetimes and branch-relative truncation; simultaneous commit/recovery/completion priorities; and identity-safe late-result handling after physical reuse.

This is substantial feature integration even if the solver chooses a small clean reconstruction algorithm. Increasing the number of tokens or files, hiding an event rule, banning a simpler implementation, shortening the budget, or demanding a particular microarchitecture would not be acceptable substitutes for that work.

## Shortcut review and valid alternatives

- The v1 blind patch cannot repair absent storage and transition machinery. Review the actual new starter for accidental inclusion of those structures, not just textual difference from v1.
- A complete clean rewrite using an ordered record list plus map reconstruction is allowed. Recreating a familiar algorithm from the contract is legitimate skill, not a shortcut to prohibit.
- Single-lane serialization, rejecting all branches, or draining before dispatch cannot pass the already-public maximal-prefix acceptance requirement. This is an existing product requirement, not a hidden v2 performance constraint.
- Any legal free-register priority remains valid. Separate counters, masks, queues or recomputation may be used. Invalid output fields remain unconstrained.
- Private tool/isolation/bit-serialization infrastructure may be adapted from v1. The oracle and reference must be extended and separately validated for alias behavior; the old unique-destination assertion is invalid for moves. Candidate-facing legacy sources remain newly authored. Record their provenance and exact reused-file hashes. Do not provide the old repaired code, blind patch, reviews, desired pass ratio or private assets to fresh candidates.

## Difficulty hypothesis and batch boundary

Hypothesis: replacing a mostly solved implementation with a realistic legacy migration requires enough original integration reasoning to reduce success compared with a three-condition repair. This is unmeasured. A strong model may still implement a correct compact design quickly; five fresh trials are necessary to assess the observed result. The objective is 1 pass in that five-trial batch, not proof of a population probability or permission to discard other outcomes.

Scope is one v2 redesign, contract/starter review, implementation/validation and a root-controlled freeze. Root owns exactly one five-trial batch and all spend; then the project pauses even if the observed ratio differs. Author runs no model trials, creates no extra agents, commits nothing, and makes no further redesign until the root reports that batch.

## Requested judge decision

Review whether unchanged behavior plus the proposed legacy implementation is a material, realistic integration task; identify remaining near-complete-solution leaks or trivial repairs; confirm that clean rewrites remain legitimate; challenge the difficulty hypothesis without estimating an unsupported pass probability. Approve or request a bounded revision before implementation.

## Scope boundary and added semantic controls

Root's final scope is move-alias-only; read leases and any extra reader protocol are excluded. The required private controls include: treating moves as new allocations; clearing ready on a ready alias; setting shared ready on move acknowledgement; overwriting inherited readiness with the last alias record's done bit; reclaiming a tag still referenced by another committed alias; retargeting a move when its source architectural register is later overwritten; incorrect zero/self-move metadata; refusing move dispatch at zero free-register capacity; and branch/lane-boundary errors affecting aliases. Retain prior sparse completion and bit-preserving invalid-output regressions. Validate a legitimate alternative allocation strategy and a valid invalid-lane-X implementation.


## Final bounded decision

Apply the judge's alias reclamation wording and reachable-capacity guidance, then close the contract before implementation. The actual starter must be a newly authored working single-inflight legacy path, not the v1 oracle with more predicates inverted. Candidate must develop multi-record state transitions, alias readiness provenance, exact two-lane admission and rollback/retirement ownership. We explicitly accept a clean reconstruction solution and cannot promise that only one of five Astra attempts will succeed. Root owns exactly that one batch and pauses afterward.
